PRD-001 — Orient the factory to this repo

A short conversation to get your project's first issues filed.

Before we start

Point your coding agent at docs/AGENT-QUICKSTART.md in the vendored entropy-machines directory. It needs that context to work the issues this PRD creates.

You answer this doc; the agent works from what you decide.

entropy-machines is a workflow for running coding agents on a real codebase. It keeps agents from stepping on each other's work and makes sure nothing lands without proof.

upstream, not downstream A PRD creates work here — work does not create a PRD. The pages ahead file your first tracker issues.

The cycle

ISSUES ──▶ WORKED ──▶ VERIFIED ──▶ FOLDED ──▶ SPRINT REPORT ──▶ ISSUES

Full stage-by-stage version: doctrine/WORKFLOW.md. You don't need it to follow this page.

Who does what

RoleDoes
You (owner) Answer the open questions ahead, say when work can merge, close the sprint when you're satisfied.
Worker Takes one scoped issue, works in its own git worktree, leaves a HANDOFF.md when done.
Verifier Sweeps all finished work for the sprint on a clean tree and reports a verdict.
Orchestrator Dispatches work, folds verified changes into main, turns your rulings into issues.

Full role definitions: doctrine/ROLES.md.

The harness has guardrails throughout — dispatch refuses dirty bases, commits are refused without handoff records, nothing lands without verification. Details in doctrine/WORKFLOW.md.

Test suites

Which tests run and when — something we'll work out together.

The harness can run your test suites at two points: on every fold (gating), or once per sprint via the verifier (advisory). Fast tests usually gate; slow or flaky ones run advisory. This ends up in config.json's suites array.

If you already know what suites you have and how you'd like them treated, write that below. If not, that's fine — most people getting started here don't have this nailed down yet, and that's exactly what the first few sprints help sort out.

If you know your test commands and which should block a landing, list them here. Otherwise leave this open — we'll figure it out together as we explore the project. The agent that fills in the "What we found" page will have a head start on this.

Protected paths

Files no agent should edit without your say-so.

Paths in project.protectedPaths are off-limits to dispatched workers. Think generated bundles, public API surfaces, or schema migrations — anything where an unsupervised edit could hurt.

If something comes to mind, list it below. If nothing does, that's normal for a project just getting started. You can add paths later the first time an agent touches something you wish it hadn't.

List any files or directories you'd rather agents not touch on their own. If you're not sure yet, leave this open — it's easy to add to later, and the first sprint or two will make the right list obvious.

How work gets folded in

Not a policy to declare up front — a conversation you have with the orchestrator as you go.

When a worker finishes and the verifier confirms it, the orchestrator folds the change into main. How much of that process you want to see is something you work out together.

Early on, you'll probably want to check in on every fold. As you build trust in the loop, you might let the orchestrator fold verified work on its own and only pull you in when something is held or uncertain. Either way, you steer this by giving feedback in the moment — not by setting a standing policy.

How hands-on do you want to be right now? "Check with me on everything" and "fold what's verified, flag what's uncertain" are both fine starting points — and you can adjust as you go. There's no wrong answer, and it's not permanent.

Getting started

Two ways in, depending on where you are.

Option A — Design first. Work with a designer agent to nail down what you're building. Those sessions generate issues for the factory while subagents explore the repo and get a head start on the codebase.

Option B — Build first. You already have issues in mind and want to start shipping. We'll put training wheels on the first few PRDs so you can learn the loop while getting real work done.

Pick whichever fits, or describe your own starting point.
