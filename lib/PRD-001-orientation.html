PRD-001 — Orient the factory to this repo

The first document you fill in here. Answering it files your project's first real issues.

entropy-machines is a workflow for running coding agents on a real codebase without letting them corrupt each other's work or land things nobody proved. It is four roles and a handful of gates, each one built because something specific went wrong once.

upstream, not downstream A PRD is the artifact that creates work here — work does not create a PRD. Filling in the questions on the following pages is what files your first tracker issues; a one-off "discovery" task is never the entry point, it's one issue that might fall out of an answer below.

The cycle

ISSUES ──▶ WORKED ──▶ VERIFIED ──▶ FOLDED ──▶ SPRINT REPORT ──▶ ISSUES

Full stage-by-stage version, including the incidents each stage's rules were built to stop recurring: doctrine/WORKFLOW.md. You should not need to open it to follow this page.

Four roles

RoleDoesNever
Owner (you) Rules on open questions like the ones ahead, says when held work may merge, ticks the sprint closed. Delegates the sprint-close tick or a decision an issue is gated on — there is no code path to either.
Worker Implements one scoped issue, in its own git worktree, leaves a HANDOFF.md. Commits, pushes, merges, or edits outside its declared file scope.
Verifier Sweeps all finished work for the sprint, once, on a clean tree; reports a verdict. Fixes, lands, or repeats a number it did not personally re-run.
Orchestrator Dispatches, folds verified work into main (the only committer), turns rulings into issues. Lands held work without your go-ahead, or relays a worker's own claim as if it had re-run it.

Full definitions, including what each role must not do and why: doctrine/ROLES.md.

What the gates protect you from

  • bin/dispatch refuses to run from anywhere but the repo root, refuses uncommitted edits already sitting in the files it's about to hand out, and refuses to overlap a file another live dispatch already holds — a worker never starts from a wrong or dirty base.
  • The commit-msg hook refuses a commit that lands a dispatched issue with no handoff record for it — a worker's changed/found/assumed/next is never lost to a fast commit.
  • The pre-commit hook refuses a commit touching a watched path with no changelog.d/ fragment — nobody has to reconstruct what changed by reading the diff (off entirely if changelog.enabled is false).
  • bin/handoff refuses --verified text that just relays what the worker claimed — "tests pass" is not evidence, you have to say what you re-ran.
  • The tracker refuses status=held outright — held-ness lives in heldWhy, gated-ness in gate, and neither is a status value, so a hold with no reason attached cannot be created.

That is everything you need to read the rest of this document. The next page is what an agent found looking at your actual repo; the pages after that are yours to rule on.

Which suites gate a landing, and which are advisory?

This becomes entropy.json's suites array.

Every entry under suites runs in the verifier's sweep and in bin/post-fold-audit. An entry tagged "slow" can be skipped with --skip slow — that is the built-in way to say "don't block every single fold on this one," which in practice is what makes a suite advisory rather than gating (docs/CONFIG.md).

Option A — a small, fast set gates every fold (say, typecheck + unit); anything slow or flake-prone (e2e, integration) is tagged "slow" and only required once per sprint via the verifier, not on every single dispatch. Cost: a red slow suite can sit underneath a landed fix for a while, surfacing on your own review cadence instead of blocking immediately.
Option B — everything in suites gates every fold, nothing tagged slow. Cost: every dispatch cycle pays the full suite's wall time and flake rate, even for a one-line fix.
I'd take A — start with typecheck + unit gating, tag anything slow or historically flaky, and widen the gate later once you trust it. Which suites do you have (or plan to have), and which of them gate vs. which are advisory?

What belongs in project.protectedPaths?

Paths no dispatched agent may edit on its own initiative.

Candidates: an append-only interface, a generated bundle, a cross-writer contract, anything that needs a human holding both ends. A worker (and the unattended drainer, if you ever arm it) refuses to touch a listed path; the drainer's runner also diffs finished work against the list before pushing and quarantines the whole run on a match.

Option A — start narrow: only what you can name right now (a generated bundle, a public API surface, a schema migration you don't want an agent improvising on). Cost: something you forgot is editable by a worker until you notice and add it.
Option B — start wide: anything that took real design thought, docs included. Cost: workers stall asking to touch ordinary files, and "held, needs owner" piles up for things that never needed protecting.
I'd take A — the list only blocks automated edits, not yours; you can always add to it the first time a worker touches something you regret. What paths go in it?

Keep the built-in file tracker, or point at one you already use?

This becomes tracker.backend.

The harness needs exactly six operations from a tracker — show, notes, remember, claim, ready, set (no add; an issue is created with set, which auto-vivifies). "file" is the built-in backend, storing .entropy/issues.json locally. "command" shells out to any executable implementing the same six ops (docs/TRACKER-ADAPTER.md) — and that adapter has to be able to express held (a heldWhy field) and gated (a gate field) correctly, or ready will over-report what's actually claimable.

Option A — keep "file". Zero setup, works today, per-checkout state under .entropy/ (gitignored). Cost: not shared across machines, no UI beyond bin/tracker show.
Option B — point tracker.command.bin at an adapter for a tracker you already run. Cost: someone has to write and maintain that adapter, and get held/gated right, or claimable work is reported wrong.
I'd take A to start — nothing about the workflow depends on which backend answers bin/tracker ready, so migrating later costs nothing you wouldn't pay anyway. File-backed, or point at something else?

Does verified work land on your say-so every time, or on the verifier's word?

Not a config key — a policy for how the orchestrator behaves.

The two doctrine docs phrase this slightly differently. doctrine/WORKFLOW.md ties your say-so specifically to held work: "Nothing is folded while work is HELD. The owner says when." README.md's summary states it more broadly: "Nothing lands eagerly. Finished work is held until the owner says merge." Read literally, the first lets the orchestrator fold anything verified and not explicitly held, on its own judgment; the second reads as every fold waiting on you. Worth ruling on explicitly rather than each orchestrator session guessing which reading you meant.

Option A — owner-gated: the orchestrator checks in with you before every fold, even something verified and not held. Cost: a check-in step per issue or per sprint; slower cadence, but nothing lands without you seeing it first.
Option B — verifier-gated: the orchestrator folds automatically once the verifier reports healthy and the issue isn't held; you brake specific issues with heldWhy. Cost: faster, but you only get asked when the orchestrator is unsure — you have to actually use heldWhy proactively.
I'd take A for a new project — until you've seen a few sprints go cleanly and trust the verifier's sweep and your own review habits, then reassess toward B. Which do you want?

What turns this from orientation into a project?

The one question above that isn't config at all.

Everything on the previous four pages configures the harness. None of it is a real feature or bug fixed yet. This is the question whose answer becomes the first issue dispatched to an actual worker.

Option A — dispatch a verification issue first: confirm the "What we found" page for real and finish entropy.json (suites, generate, worktree links). Cost: one dispatch cycle spent on bookkeeping before touching a real feature or bug.
Option B — skip straight to a real feature or bug you already know needs doing, and patch entropy.json's gaps opportunistically as a worker or verifier hits them. Cost: your first few dispatches run against unverified suites and paths, so a failure might be the harness's config rather than the actual work.
I'd take A if anything on the "What we found" page is marked unverified; B if you already trust your own toolchain commands and just want to see the loop move. What's the first real issue, and which order?
