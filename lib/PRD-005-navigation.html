Navigation is broken

Every page type needs a way to reach every other page type. Right now, most can't.

The harness produces four kinds of pages: PRDs (dialogue docs with response boxes), issues (the tracker view), sprint reports, and docs (everything else — quickstart guides, adapter specs, conference lists). A reader on any of these should be able to get to any of the others without going back to the terminal.

Today that doesn't work. Here is what's broken:

Generated pages are dead ends TRACKER.html, DOCS.html, PRDS.html, and REPORTS.html are generated by doctracker.py and bin/tracker render. They have no sidebar and no consistent nav bar. Once you're on the tracker, you can't get to a PRD without editing the URL or going back to the terminal.
Sprint reports are invisible Sprint reports (SPRINT-REPORT-*.html) are not tracked in manifest.json. The Reports landing page shows zero docs. There's no way to discover them through the UI.
Nav categories don't match reality The current DOCNAV patch injects five links — issues, PRDs, reports, docs, other — but "other" just points to DOCS.html (same as "docs"), and INDEX.html ("questions") was removed because it wasn't useful. The categories were never decided by the owner.

The five questions on the following pages will define the navigation system. Each one gates an implementation issue.

What are the categories?

The nav needs a fixed set of categories. Each gets a link and a landing page.

Right now the codebase assumes four categories based on handle prefixes: prd-* for PRDs, doc-* for docs, BUILD-REPORT-* or sprint-* for reports, and everything else as "other." The DOCNAV patch renders five links (issues, PRDs, reports, docs, other), but "docs" and "other" go to the same page.

Where does the nav go?

Sidebar, header bar, or both — and does every page type get the same treatment?

PRDs and other dialogue docs have a 296px sidebar with page-internal navigation (p0, p1, p2…). The sidebar is where DOCNAV currently injects category links — below the page nav, above the footer. Generated pages (TRACKER.html, DOCS.html) have no sidebar at all; some have a small header bar with a few links, but it's inconsistent.

The question is whether category nav should be:

  • Option A — Sidebar for docs, header for generated pages. Docs keep the category links in the sidebar (where they already are). Generated pages get a consistent header bar. Two different implementations, but each fits its page type.
  • Option B — Header bar everywhere. Every page gets a horizontal nav bar at the top with category links. Docs keep their sidebar for page-internal nav only. One implementation, consistent across page types.
  • Option C — Something else. Maybe category nav is a top bar and page nav is a sidebar, and both are always present. Or maybe generated pages should get a sidebar too.
The sidebar currently holds both page-internal nav (p0, p1…) and the DOCNAV category links. Adding more links there risks crowding it, especially on smaller screens. A header bar is simpler and consistent, but it means changing the layout of every dialogue doc. Generated pages need nav regardless — they're dead ends today. Which option works, or what's your alternative?

How do sprint reports get into the system?

Reports aren't tracked anywhere the nav can find them.

Sprint reports (SPRINT-REPORT-*.html) live in the docs directory alongside PRDs, but they're not in manifest.json. The manifest only tracks dialogue docs — pages with response boxes that doctracker.py manages. Sprint reports are generated by bin/sprint-report and don't have response boxes.

This means:

  • REPORTS.html (the landing page) is empty — doctracker.py has nothing to list.
  • Sprint reports don't get enhance.py patches (no theme selector, no DOCNAV, no live reload).
  • There's no way to discover sprint reports through the UI.
There are two clean options. (A) Add sprint reports to manifest.json alongside PRDs — bin/sprint-report would register each report when it generates one, and doctracker.py would list them on REPORTS.html the same way it lists PRDs on PRDS.html. This also means they'd get enhance.py patches. (B) Have the Reports landing page scan the docs directory for SPRINT-REPORT-*.html files directly, without touching the manifest. Simpler, but sprint reports stay outside the tracking system and don't get enhance patches. Which approach, or something else?

How do generated pages get nav?

Three approaches, each with a trade-off.

Generated pages (TRACKER.html, DOCS.html, PRDS.html, REPORTS.html) are written by Python scripts and currently have no consistent nav. They need category links like every other page. The question is how they get them:

  • Option A — Bake it into the generator templates. Each generator (doctracker.py, bin/tracker render) includes the category nav HTML directly in its template. Simple, but the nav HTML is duplicated across generators, and updating it means touching every template.
  • Option B — Have enhance.py patch them. The same way it patches dialogue docs. Currently generated pages are in the GENERATED set and get skipped by enhance — that would change. Centralizes the nav in one place, but enhance.py would need to handle pages without a sidebar.
  • Option C — Have serve.py inject it at serve time. The server injects nav HTML into every response. No files are modified on disk. But the nav only works when served — opening a file directly shows no nav.
Option B (enhance.py) is the most consistent — one place for the nav, applied to every page type. But it means generated pages can no longer skip enhance, and enhance needs to handle the no-sidebar case (inject a header bar instead). Option A is simplest but means nav duplication. Option C only works when served. Which approach, or a mix?
