This PRD replaces the HTML template + enhance.py system with a React SPA backed by SQLite. The SPA becomes the primary surface for human-agent collaboration — not just a doc viewer.

PRD-006 — Why this migration

The current system has hit two limits: one technical, one conceptual.

The technical limit

enhance.py is 1,568 lines of regex-based HTML surgery across 10+ patch passes. Every cross-cutting change (themes, nav, categories) requires touching 4+ files and produces ordering bugs. The nav-category-order bug, the theme flash, the var-fallback drift — these are symptoms of patching HTML strings instead of rendering from components.

The conceptual limit

The current system treats the browser as a read-and-respond surface: the user opens a doc, types in response boxes, saves. Agents live in the terminal — they edit files, the user reads the result in the browser, types a response, and the agent reads that response from disk. Every exchange requires a round-trip through the filesystem.

That loop is the real bottleneck. Not enhance.py's regex — the fact that humans and agents can't work in the same place at the same time.

The shift The SPA becomes the collaboration surface between humans and agents. Agents read and write through an API. The user sees agent activity in real time — replies appearing, issues updating, status changing — without leaving the browser. The terminal becomes the agent's workspace, not the user's. The goal is that a non-technical owner can run their project from the browser entirely.

The SPA as collaboration surface

How humans and agents work in the same place.

Today's flow (terminal-mediated)

Owner opens PRD in browser → reads → types response → saves
Agent reads response from disk → writes reply to file → commits
Owner reloads browser → reads reply → types response → saves
  (repeat, with a terminal session brokering every exchange)

Target flow (SPA-mediated)

Owner opens PRD in browser → reads → types response → saves (POST to API)
API writes to SQLite → notifies agent via event/webhook
Agent reads response via API → writes reply via API → API writes to SQLite
SPA receives update via WebSocket → owner sees reply appear in real time
  (no terminal needed for the owner; agent works via API)

What this enables

  • No file:// dependency — the SPA is the interface, the server is the brain. For offline/sharing, an "Export to HTML" button snapshots any page as a standalone file.
  • Agent presence — the SPA can show when an agent is reading a doc, writing a reply, or working an issue. The owner sees work happening, not just results.
  • Inline conversation — instead of response boxes that an agent reads asynchronously from disk, responses and agent replies render as a conversation thread. No round-trip through the filesystem.
  • Non-terminal users — a project owner who isn't a developer can open the SPA, review PRDs, approve issues, read sprint reports, and interact with agents entirely from the browser.

What this does NOT require

Real-time push (WebSockets) is a phase 2 feature. Phase 1 works with polling, same as today's /__docversion. The architecture supports both — the database is the source of truth either way. The SPA polls for changes; later, the server pushes them.

The target flow collapses the terminal out of the owner's workflow entirely. Two questions: (1) How much of this should be in the initial migration vs. built incrementally on top? The SPA + API + database can ship first as a better version of what exists (no enhance.py, real data model), with real-time and agent API added as follow-on issues. (2) Are there other roles besides "owner" who would use the SPA? Reviewers, team members, stakeholders who only read reports? Multi-user changes the auth and data model.

Database design

SQLite replaces issues.json, localStorage, manifest.json, and embedded response data.

Why SQLite

Single file, zero external dependencies, Python has it built in (sqlite3), Node has excellent drivers (better-sqlite3). Keeps the "no external services" property. The file lives at .entropy-machines/entropy-machines.db alongside the current issues.json. If the project outgrows SQLite, the schema migrates to Postgres with minimal code changes.

Schema

-- Core content
docs (
  id          TEXT PRIMARY KEY,   -- "PRD-002-dialogue-workflow"
  title       TEXT NOT NULL,      -- "PRD-002 — How dialogue docs are worked through"
  short_name  TEXT NOT NULL,      -- "PRD-002"
  type        TEXT NOT NULL,      -- "prd" | "report" | "doc"
  status      TEXT DEFAULT 'open',-- "open" | "in-review" | "answered" | "closed"
  foot        TEXT,               -- footer guidance text
  created_at  TEXT,
  updated_at  TEXT
)

pages (
  id          TEXT NOT NULL,      -- "p0", "p1", ...
  doc_id      TEXT REFERENCES docs(id),
  position    INTEGER NOT NULL,   -- ordering
  nav_group   TEXT,               -- "Context", "Open questions", etc.
  nav_title   TEXT NOT NULL,      -- "What a dialogue doc is"
  heading     TEXT NOT NULL,
  subtitle    TEXT,
  content     TEXT NOT NULL,      -- HTML body of the page
  PRIMARY KEY (doc_id, id)
)

-- Response / conversation
responses (
  id          INTEGER PRIMARY KEY,
  doc_id      TEXT REFERENCES docs(id),
  page_id     TEXT,               -- matches pages.id
  resp_key    TEXT NOT NULL,      -- "p0-key-question" (stable identity)
  label       TEXT,               -- "Your overall read"
  discuss     TEXT,               -- the discussion prompt HTML
  value       TEXT DEFAULT '',    -- the owner's answer
  updated_at  TEXT,
  UNIQUE(doc_id, resp_key)
)

-- Agent replies (the conversation thread)
replies (
  id          INTEGER PRIMARY KEY,
  response_id INTEGER REFERENCES responses(id),
  author      TEXT NOT NULL,      -- "agent" | "owner"
  content     TEXT NOT NULL,
  created_at  TEXT
)

-- Issues (replaces issues.json)
issues (
  id          TEXT PRIMARY KEY,   -- "i-react-scaffold"
  title       TEXT NOT NULL,
  status      TEXT DEFAULT 'open',-- "open" | "progress" | "review" | "done"
  source_doc  TEXT REFERENCES docs(id),  -- PRD/report/doc that created this issue (optional)
  blocked_by  TEXT,               -- JSON array of issue ids
  claimed_by  TEXT,
  claimed_at  TEXT,
  created_at  TEXT,
  updated_at  TEXT
)

-- Issue notes (replaces the notes log)
issue_notes (
  id          INTEGER PRIMARY KEY,
  issue_id    TEXT REFERENCES issues(id),
  type        TEXT NOT NULL,      -- "dispatch" | "handoff" | "comment"
  author      TEXT,
  content     TEXT NOT NULL,
  created_at  TEXT
)

-- Settings (replaces localStorage for theme, replaces manifest.json)
settings (
  key         TEXT PRIMARY KEY,   -- "theme", "doc:PRD-002:version", etc.
  value       TEXT
)

Relationships

  • docs → has many pages (ordered by position)
  • docs → has many responses (one per response box)
  • responses → has many replies (the conversation thread)
  • issues → has many issue_notes
  • settings — flat key/value, replaces scattered config

Migration path

A one-time migration script reads the existing data sources and populates the database:

  1. Parse each HTML doc → extract pages, response boxes, saved answers → insert into docs, pages, responses
  2. Read issues.json → insert into issues + issue_notes
  3. Read manifest.json → insert into settings
Decisions made: (1) Issues and docs are linked — source_doc TEXT REFERENCES docs(id) is in the schema. The tracker can show "created by PRD-001" and docs can list their spawned issues. (2) Per-user storage is deferred — no multi-user requirement in scope yet. Anything else on the schema?

Agent API

How agents interact with the system without touching files.

The principle

Agents should never need to parse HTML, read localStorage, or edit response data in a file. Every action an agent takes goes through the API. Agents interact via an MCP server that exposes tools (post_reply, claim_issue, list_responses, etc.) — the agent calls tools directly without knowing the underlying HTTP or database. The API writes to SQLite; the SPA sees the change.

Endpoints

EndpointMethodWhat it does
/api/docsGETList all docs with metadata, status, answered/total counts
/api/docs/:idGETFull doc with pages and responses
/api/docs/:id/responsesGETAll responses for a doc (what the owner wrote)
/api/docs/:id/responses/:keyGET/PUTRead or update a single response
/api/docs/:id/responses/:key/replyPOSTAgent posts a reply to a specific response
/api/issuesGET/POSTList or create issues
/api/issues/:idGET/PATCHRead or update an issue
/api/issues/:id/notesGET/POSTRead or add notes to an issue
/api/settings/:keyGET/PUTRead or update a setting (theme, etc.)
/api/eventsGET (SSE)Server-sent events stream for real-time updates (phase 2)

MCP server

An MCP server wraps the REST API so agents interact through native tool calls:

post_reply(doc="PRD-002", response="p0-key-question", text="...")
list_responses(doc="PRD-002")
claim_issue(id="i-react-scaffold")
list_issues(status="open")
create_issue(id="i-...", title="...")

Agents never construct URLs, parse HTML, or know about HTTP. The MCP server is the single agent contract — it replaces both the current file-editing pattern and the need for any CLI wrapper. Agent onboarding docs update in phase 2 alongside the MCP server.

What bin/tracker becomes

bin/tracker currently reads/writes issues.json directly. After migration, it becomes a thin wrapper around the API — same CLI interface, different backend. The dispatch/handoff pipeline keeps working unchanged.

The MCP server becomes the single agent contract — agents call tools like post_reply and claim_issue directly, without knowing HTTP or file paths. The current file-based workflow (editing HTML, reading issues.json) is fully replaced. Agent onboarding docs update in phase 2 alongside the MCP server. Key component: ResponseBox + ReplyThread

This is the core of the collaboration model. A ResponseBox renders the discussion prompt, the owner's textarea, and a ReplyThread beneath it showing agent replies. When the owner saves, the response goes to the API. When an agent posts a reply, the thread updates (via polling in phase 1, push in phase 2).

The React app lives in ui/ at the repo root — standard convention, clean separation from the Python backend in lib/. Vite's dev server proxies API calls to the backend during development; in production, the server serves the built ui/dist/ as static files and handles API routes. React Router handles navigation — hash-based routing isn't necessary since the server can catch-all to index.html. Anything else about the component tree or routing that needs revisiting?

Migration strategy

Incremental build, late delete, commit along the way.

Based on your input: build the new system alongside the old one. Confirm behavior at each step. Delete the old system only after the new one is verified and stable. Commit and push throughout so any step can be reverted.

Phase 1: Foundation

  • Initialize Vite + React + TypeScript in ui/
  • Create SQLite database schema + migration script from existing data
  • Add /api/* endpoints to the server
  • Build dashboard and tracker as React pages (simplest — no response boxes)
  • Server serves both: React app at /, old HTML docs still accessible

Phase 2: Doc renderer + agent API

  • Build DocPage with response boxes, reply threads, autosave, save via API
  • Build MCP server wrapping the REST API — agents interact via native tool calls
  • Update agent onboarding docs (AGENT-QUICKSTART, WORKFLOW) for MCP workflow
  • Migrate all 10 docs (5 PRDs, 3 reports, 2 extras) to database
  • Verify: every response preserved, every page renders correctly
  • Build landing pages as React components
  • Build "Export to HTML" for offline/sharing

Phase 3: Cleanup

  • Confirm all pages render correctly from the React app
  • Delete: enhance.py, HTML templates, theme flash, old serve paths
  • Delete: issues.json read/write paths (replaced by SQLite)
  • bin/tracker now wraps the API instead of reading JSON directly

Phase 4: Real-time (follow-on)

  • Replace polling with Server-Sent Events or WebSocket
  • Agent presence indicators in the SPA
  • Live reply appearance (agent posts reply → owner sees it immediately)
  • Notifications (new reply on a response you wrote, issue status change)
Phase 1 ships a working React app with dashboard + tracker while the old doc system keeps running. Phase 2 is the heavy lift — doc rendering and data migration. Phase 3 is cleanup. Phase 4 is the real-time collaboration that makes this worth doing long-term. Does this phasing make sense? Should any phase be split further or reordered? Is phase 4 actually phase 2 — is real-time collaboration the thing you want soonest?

Dev workflow

  • npm run dev (inside ui/) starts Vite with HMR, proxies /api/* to the server
  • npm run build produces ui/dist/
  • Server detects ui/dist/ and serves it; falls back to old HTML if missing
  • Server stays Python — it gains API endpoints but keeps its existing role

What about going full Node?

Replacing the Python server with Express/Fastify would mean one language everywhere. But the current server is 872 lines of tested, working code that integrates with bin/tracker, docstate.py, and the dispatch/handoff pipeline. Rewriting it in Node is a lot of work for marginal gain. The recommendation is: keep Python as the backend, add API endpoints to the existing server, use React for the frontend.

Decisions made: (1) ui/dist/ is NOT committed to the repo — Node is a dev dependency, and npm run build produces the static output. This keeps the repo clean and avoids rebuild-before-commit friction. (2) React 19 is the framework — the ecosystem, agent familiarity, and trajectory of this project toward multi-user collaboration justify it over lighter alternatives. Token cost impact

The migration significantly reduces agent token consumption per interaction.

OperationBefore (file-based)After (MCP + API)
Read one responseRead entire HTML file (20-40K tokens — includes CSS, JS, nav, template boilerplate)MCP tool call returns JSON (~500 tokens)
Post a replyRead file + write back full file with edit (~40-80K tokens round-trip)MCP tool call with reply text (~200 tokens)
List open issuesRead issues.json (~2-5K tokens, grows with history)MCP tool call returns filtered list (~500 tokens)
Update issue statusRead + write issues.json (~4-10K tokens)MCP tool call (~100 tokens)

Agents never see HTML, CSS, or React components — they interact only with structured data through MCP tools. This is a 10-20x reduction in tokens per interaction, which compounds across every agent task in a sprint. Track actual token usage before and after phase 2 to validate.

What stays exactly the same

  • bin/dispatch / bin/handoff — the agent workflow pipeline is git-based, unaffected
  • bin/tracker CLI interface — same commands, different backend
  • Test suite — cases test behavior, not implementation; most pass unchanged
  • The 5-color theme system — same colors, same vars, applied by React instead of inline JS
  • Response box UX — same autogrow, same filled state, same save button
The before/after table shows that the user-facing behavior stays almost identical — the same pages, the same response boxes, the same themes. What changes is the plumbing underneath: components instead of patches, a database instead of scattered files, an API instead of filesystem round-trips. The biggest visible change is that agent replies will appear as conversation threads instead of reply folds in HTML. Does this mapping look right? Anything that should stay file-based instead of moving to the database?
